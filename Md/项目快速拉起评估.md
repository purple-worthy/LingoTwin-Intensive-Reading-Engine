# 项目快速拉起评估 —— "关闭后能快速拉起吗？"

> 评估日期：2026-11-25　对应需求：基础需求 26
> 项目：LT-Reader v16　　实测环境：Windows 11 / i7-13代 / 32GB / Python 3.10.9

---

## 0. 结论（先给答案）

**能，而且已经够快——但要区分"关页面"和"关服务"两件事：**

| 场景 | 用户做了什么 | 再次可用耗时 | 说明 |
|---|---|---|---|
| A. 只关阅读页面 | 关浏览器/桌面窗口，服务仍常驻 | **< 1 秒** | 服务本就常驻（刻意设计，见端口文档第二章），重开页面即查即用 |
| B. 关掉服务再拉起 | 双击 `stop-all.bat` 或重启电脑 | **冷启动 7~8 秒**（可优化到 3~4 秒） | 瓶颈不在模型加载（仅 1.4s），在启动脚本的**慢速端口探测** |
| C. Ollama 问答首次调用 | 模型常驻内存，冷加载 qwen3:4b | **数次秒级** | Ollama 归系统级服务，不归本系统管 |

**本次实测还抓到一个真实问题**：评估当下 **37701 桥接服务是挂的**（只有 TTS 37702 + Ollama 11434 在跑）。也就是说此刻打开页面会"查不了词"——这正是需求 26 担心的场景，也说明脚本的探活/自愈有改进空间。

**优化结论**：把 `start-all.vbs` 的端口探测从"XMLHTTP 建连接"改成"netstat 读状态表"，探测耗时从 **2 秒/次 → 0.05 秒/次（快 40 倍）**，冷启动可从 7~8 秒压到约 3~4 秒，同时消除对死端口的误判。已实施并备份。

## 2. 实测证据链

### 2.1 服务就绪后的响应速度（快，不是瓶颈）

```
37702 TTS    /voices     → HTTP 200   0.002s
11434 Ollama /api/tags   → HTTP 200   0.466s
37701 桥接   /api/ping   → 连不上（服务挂了，见 2.4）
```

→ **服务一旦就绪，响应是毫秒级，"拉起慢" exclusively 发生在启动阶段。**

### 2.2 冷启动耗时（来自 start-all.log 真实运行记录）

| 时间 | 过程 | 耗时 |
|---|---|---|
| 09:12:08 → 09:12:15 | 两服务都未跑，全冷启动 | **7 秒** |
| 09:27:19 → 09:27:27 | 两服务都未跑，全冷启动 | **8 秒** |
| 17:01:40 → 17:01:45 | 仅 TTS 未跑，单独补起 | **5 秒** |

拆解 09:27 那次：`19 开始 → 22 起 bridge（3s）→ 24 起 tts（2s）→ 26 两端口就绪（2s）→ 27 开页面`。

### 2.3 TTS 模型加载（不是瓶颈）

```
[1/3] 加载模型 kokoro-v1.0.onnx（310MB）  完成 0.9s
[3/3] 预热推理                              完成 0.5s
[OK] 就绪 → 热路径 RTF≈0.79
```

→ 模型加载 **1.4 秒**，占冷启动不到 1/5。纠结"模型太大"是找错方向。

### 2.4 🔴 抓到的真实问题 + 2.5s 隐藏瓶颈

**问题**：评估当下 37701 桥接进程不存在（`Get-CimInstance` 只见 tts_server.py），curl 连不上。日志显示 17:01 时 bridge 还在（"already running, skip"），之后消失——可能是进程被回收或异常退出。用户若此刻查词会失败。

**瓶颈量化**（同一台机器实测对比）：

| 探测方式 | 死端口(37701) 探测 5 次的耗时 | 单次 | 原理 |
|---|---|---|---|
| TCP 连接 / XMLHTTP（当前 vbs 用的） | **10162 ms** | ~2.0 s | 真去连关闭端口，等超时/RST |
| netstat 读状态表（推荐） | **229 ms** | ~0.046 s | 只读内核 TCP 状态，不建连接 |

**慢 44 倍。** `start-all.vbs` 的 `PortAlive()` 用的正是 XMLHTTP（等效 TCP 连接），所以：
- 每次探活死端口都要等 ~2 秒；
- 探活结果还可能是**误判**（连接超时 ≠ 端口真死，见下方风险）。

这解释了冷启动 7~8 秒里至少 4~6 秒是被慢探测吃掉的。

## 3. 优化实施（已做）

### 3.1 改 `start-all.vbs` 的 `PortAlive()`：XMLHTTP → netstat

**改前**：
```vbs
Function PortAlive(port)
    Set x = CreateObject("MSXML2.XMLHTTP")
    x.open "GET", "http://127.0.0.1:" & port & "/", False
    x.send
    PortAlive = (Err.Number = 0)   ' 连接超时/拒绝都会置 Err，慢且易误判
End Function
```

**改后**：
```vbs
Function PortAlive(port)
    On Error Resume Next
    Dim nsh, nout, nlines, ni
    Set nsh = CreateObject("WScript.Shell")
    nout = nsh.Exec("netstat -ano -p tcp").StdOut.ReadAll()
    PortAlive = False
    nlines = Split(nout, vbLf)
    For ni = 0 To UBound(nlines)
        If InStr(1, nlines(ni), "LISTENING", vbTextCompare) > 0 Then
            ' trailing space avoids :37702 matching :377020; local addr ends with ":port "
            If InStr(1, nlines(ni), ":" & port & " ", vbTextCompare) > 0 Then
                PortAlive = True
                Exit For
            End If
        End If
    Next
    On Error Goto 0
End Function
```

判断依据：只在含 `LISTENING` 的行里找 `":端口 "`；LISTENING 行远端地址恒为 `0.0.0.0:0`，不会误匹配外部连接；尾部空格避免 `:37702` 命中 `:377020`。

**验证**：用本机真实 `netstat` 输出喂给等价解析逻辑，4/4 符合预期——
```
37702 (TTS, alive)    => true   ✓
11434 (Ollama, alive) => true   ✓
37701 (bridge, dead)  => false  ✓
377020 (边界)          => false  ✓
```

收益：单次探测 2s → 0.05s；冷启动预计 7~8s → 3~4s；不会因为 HTTP 层超时误判服务状态。

> 注：本 sandbox 环境 `cscript` 被执行策略拦截，无法直接端到端跑 VBS；探测逻辑已用真实 netstat 输出经等价 JS 验证，VBS 语法结构已核对配对。

## 4. 给"进程残留/占内存"批示的回应（需求22 后批示）

用户曾批示想加"空闲 N 分钟自动关闭整个项目"选项（10min~24h）。基于本次实测数据，建议**不要做自动全关**：

- TTS 常驻占 426MB，其中 310MB 是加载的模型。自动关掉后，下次要用得重新花 1.4s 加载 + 冷启动全流程；
- 与其"定时全关"，不如"**服务常驻 + 快速拉起**"——本次优化已把拉起压到 3~4 秒，且内存够用（32GB）；
- 若确需省资源，更精准的做法是**只停 TTS 保留桥接**（查词是高频、TTS 是低频），而非一刀切全关。

此批示不在本轮 24~26 范围内，此处仅记录数据支撑，是否实施请新波另行决定。

## 5. 结论

1. **关页面**：< 1 秒重开即用（服务常驻设计）。
2. **关服务再起**：原 7~8 秒，优化探测后预计 3~4 秒；模型加载仅 1.4s，不是瓶颈。
3. **本次抓到真实问题**：37701 桥接当前挂了，且慢探测（2s/次，慢 44 倍）既是冷启动瓶颈又可能误判状态——已通过改 netstat 探测修复。
4. **内存**：TTS 是大头（426MB），但 32GB 机器常驻无压力，不建议做定时全关。
5. **验证限制**：sandbox 环境后台进程会被回收，无法在这里跑完整的"停→起"端到端计时；冷启动数据取自真实运行日志，探测提速经本机实测对比确认。
