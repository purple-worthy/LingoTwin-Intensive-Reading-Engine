在 `Setting` 中加入 MySQL 连接配置，核心目的是**让这套纯前端 HTML 精读引擎突破浏览器沙盒的三大物理限制，升级为可长期积累的“全量词库 + 个人知识库”底座**。

具体有 4 个实际意义：

1. **挂载 340 万全量 ECDICT 词库，摆脱内存与文件大小限制**
   浏览器内置的 `IndexedDB` 虽然能存数据，但要把完整的 340 万条 `stardict.db` 一次性塞进网页内存里，会导致页面首次加载卡顿甚至浏览器标签页崩溃。之前我们只提取了 5 万高频词（`ecdict_50k_ready.json`）作为妥协；而一旦配置了本地 MySQL（`ecdict` 库）+ 桥接接口，网页就能**按需向 MySQL 发起毫秒级索引查询（`SELECT ... WHERE word IN (...)`）**，完整用上全部 340 万词条（包括所有生僻文学词、医学/法律专业词、古英语词形变化），几乎不占浏览器内存。
2. **实现真正的多端与多文件数据统一存储（彻底告别 C 盘端口隔离）**
   浏览器的 `IndexedDB` 是严格按“端口/路径”隔离的——你今天在 IDEA 的 `localhost:63342` 打开网页存了 3 本书，明天如果直接双击 HTML 文件（`file://`）或换个端口号打开，之前的书和翻译进度就全看不见了，且底层文件被锁死在 C 盘 `User Data` 目录的二进制碎片里。把书籍目录、已翻译段落、个人生词本全部落库到你自己建的 MySQL 后，**无论你用哪个浏览器、哪个端口、甚至以后把前端换成你规划的 Rust (Tauri) 桌面软件，连上同一个 MySQL 就能立刻看到全部历史书籍与学习进度**。
3. **构建“越用越快”的分布式翻译与词义缓存池（省掉重复大模型推理）**
   在 MySQL 中建立一张 `translation_cache`（段落译文缓存表，以英文段落的 MD5/SHA256 为主键）和 `custom_vocab`（自定义语境词义表）：
* 任何文章在调用本地 Ollama 翻译前，先去 MySQL 查一遍缓存；只要以前翻译过完全相同的句子或名著段落，**0 毫秒直接返回历史译文**，彻底省去大模型推理时间。
* 当 Ollama 遇到 ECDICT 里没有的新词并解析出结果后，自动 `INSERT` 回 MySQL 词库，实现词典的永久动态进化。


4. **为后续 Rust / Python 后端工程化预留标准接口契约**
   作为一个单文件 HTML 前端，它本质上是“纯粹的 UI 渲染层”。提前在 `Setting` 中留好 MySQL 的配置项和桥接网关地址，意味着你随时可以用几十行 Python（FastAPI）或 Rust（Actix-web / Tauri）写一个本地微服务：前端只需发 HTTP 请求，后端负责连接 MySQL 查词、读写书籍表、甚至在后台静默调度 Ollama 队列。

### 给你的实操定位建议

* **如果你只是单机轻量使用、不想后台常驻跑一个 Python/Java 接口服务**：目前你已经导入的 `ecdict_50k_ready.json` + 浏览器 `IndexedDB` + 本地 Ollama **已经完全够用**，MySQL 配置项保持留空即可，不影响任何阅读和翻译功能。
* **如果你准备把 `stardict.db` 的 340 万全量词库都导入 MySQL，或者希望以后用 Rust/Python 做长期桌面端开发**：那就可以把下载的 `stardict.db` 导入你刚建好的 MySQL `ecdict` 库中，并开启一个轻量本地桥接接口供网页调用。
