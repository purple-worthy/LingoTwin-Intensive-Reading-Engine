### 一、 5 个核心问题逐一解答

#### 1. `ecdict_50k_ready.json` 导入位置 & MySQL 网关配置怎么填？

* **导入 `ecdict_50k_ready.json` 的操作完全正确！** 点开后左上角如果显示 `本地词库: 4xxxx词`，说明 5 万高频词已经永久存入本地库了。
* **“本地 MySQL / ECDICT 词典网关配置”是干嘛的？**：
* 因为纯浏览器 HTML 出于安全机制，**无法直接用 TCP 协议连接 MySQL 的 3306 端口**，必须通过一个本地轻量后端服务（比如用 Python FastAPI / SpringBoot 写个几行的接口）来桥接 MySQL。
* 你在界面上看到的单个 URL 确实不够完整，所以在 **v9.0** 里，我把这块升级为了**完整的数据库连接配置表单（支持填写：后端桥接 API 地址 + MySQL 主机 IP + 端口 3306 + 数据库名 `ecdict` + 账号 + 密码）**，并附带一键生成的 Python 桥接脚本。



#### 2. 为什么 `qwen3:4b-instruct-2507-q4_K_M` 容易自己打断或被其他行为打断？

从你截图里的本地模型列表来看，**`qwen3:4b-instruct-2507-q4_K_M` 确实是你这批模型里最适合做实时翻译的**（`deepseek-r1:8b` 和 `qwen3:8b` 思考链太重，`bge` 是向量模型不能对话，`minicpm` 是 OCR 识图模型）。它之所以慢或容易中断，原因有三点：

1. **输出结构太重**：之前让 Ollama 既翻译句子，又输出所有新词的音标、词性、释义，4B 模型生成长 JSON 时容易因为单次 `num_predict` 耗尽或注意力退化而中途截断。
2. **页面动作打断请求**：你在解析过程中如果点击了切换章节或刷新 DOM，未加保护的请求就会被中断。
3. **不需要折腾 Redis**：本地单机浏览器已经有 `IndexedDB`（速度比走网络请求本地 Redis 还要快），加 Redis 反而增加了运维复杂度。**真正的提速秘诀是“职责拆分”**：
* **100% 查词交给 `ecdict_50k_ready.json`（0 毫秒完成）**：所有单词的音标、词性、分级、字下中文注释，全部由本地 5 万词库瞬间填好，**彻底不让 Ollama 算单词**！
* **Ollama 只做一件事——把英文段落翻译成流畅中文**：让 `qwen3:4b-instruct` 每次只吐出 1~2 句纯中文译文，不再生成复杂 JSON，**速度直接提升 5~8 倍，且几乎 100% 不会截断**！



#### 3. 之前翻译过或被打断后，为什么又从第 1 段重头开始？

* **这是上一版的逻辑缺陷**：上一版点击“解析本章”时，没有检查该段落是否已经有译文（`isTranslated`），直接把 `0 ~ N` 全部重新塞进了队列。
* **v9.0 断点续传升级**：现在点击 **`⚡ Ollama 续译未完成段落`** 时，引擎会自动扫描本章所有段落，**自动跳过已经翻译好的段落**，只从上次被打断的那一段继续往下翻译！同时在每段旁边提供 **`🔄 重译本段`** 按钮供你单独重译。

#### 4. 手动复制文章发给云端 AI（如我）后，粘贴回来的 JSON 会把本地 AI 翻译的内容覆盖吗？

* **会覆盖，但现在受你完全控制！**
* 在 **v9.0** 中，当你粘贴 JSON 点击“确认渲染”时，如果当前章节已经有部分本地 AI 翻译过的内容，系统会**自动弹出选择框**让你决定：
1. **【覆盖更新当前章节】**（保留目录位置，用你粘贴的高精度 JSON 替换当前章）。
2. **【作为独立新版本另存】**（不覆盖本地翻译，在同级目录下新建一篇对照版本）。
